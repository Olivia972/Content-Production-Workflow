# 我怎样定义业务问题

[返回 Docs 导航](../README.md)

我不会从“让AI写一篇文章”开始。我会先确认这次内容服务于什么业务、帮助谁处理什么问题，以及最终结果由谁负责。

如果业务问题没有定义清楚，AI可以生成结构完整的文字，但内容可能不支持真实决策。

## 一、先确认七项输入

| 输入 | 我需要确认的问题 | 形成的结果 |
|---|---|---|
| 业务场景 | 内容属于哪个产品、服务或业务阶段 | 场景说明 |
| 目标用户 | 谁会阅读，他当前要处理什么问题 | 用户与任务 |
| 内容目标 | 需要解释、比较、提醒、回答还是帮助决策 | 单一主任务 |
| 事实材料 | 哪些是内部知识、公开来源、用户反馈或数据 | 可用资料清单 |
| 输出载体 | 公众号、小红书、知识库、图卡还是视频脚本 | 交付形式 |
| 限制条件 | 哪些不能推断、公开或承诺 | 事实与风险边界 |
| 人工责任 | 哪些节点必须由我确认 | 审核点 |

## 二、把“写什么”改写成“帮助谁完成什么判断”

我会用下面这句话检查任务是否已经具体：

> 我需要使用【哪些已确认资料】，帮助【哪类用户】理解或完成【一个具体任务】，最终交付【什么形式】，同时不能超出【哪些事实或服务边界】。

例如，Deal站内容的任务不是“介绍一个网站”，而是：

> 使用网站近期公开内容、第三方流量资料和平台服务条件，帮助跨境卖家判断这个网站是否适合自己的产品，并了解下单前需要核对的条件；不把近期发帖样本解释成销量，也不把历史结果写成本次承诺。

## 三、区分三类信息

| 类型 | 处理方式 | 示例 |
|---|---|---|
| 已确认事实 | 可以进入正文，但保留来源和时间 | 网站近期发布内容、已提供的服务条件 |
| 业务判断 | 由我解释用途和适用条件 | 某项指标怎样用于选站或选服务 |
| 待确认信息 | 保留缺口，不让AI自行补齐 | 隐藏条件、无法识别的图标、实时规则 |

## 四、何时可以进入下一步

完成业务定义后，我至少要能回答：

- 这次内容只解决哪一个主要问题？
- 读者看完后需要理解或完成什么判断？
- 每一项关键事实来自哪里？
- 哪些结论需要我提供业务解释？
- 哪些未知项必须保留为待确认？
- 最终由谁审核并决定是否发布？

回答不清楚时，我会继续补资料或缩小任务，而不是直接让AI扩写。
